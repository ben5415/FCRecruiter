> 文档类型：产品发现（Product Discovery）与用户场景拆解  
> 文档状态：基于现有原型的回溯整理，待真实用户验证  
> 更新日期：2026-10-07  
> 关联文档：[MVP_PRODUCT_PLAN.md](./MVP_PRODUCT_PLAN.md)、[DETAILED_DESIGN.md](./DETAILED_DESIGN.md)

## 1. 文档目的

FCRecruiter 已经形成可运行原型，但此前的开发主要由功能和技术目标驱动，缺少一份明确回答以下问题的产品文档：

- 产品服务谁；
- 用户在什么时刻会使用它；
- 用户原本如何完成任务，痛点在哪里；
- Agent 为什么需要介入，以及应介入到什么程度；
- 哪些需求属于核心价值，哪些只是技术展示；
- 原型已经验证了什么，还有哪些假设没有验证。

这份文档不把事后总结包装成开发前调研。当前结论主要来自产品设想、个人使用体验和已实现原型，尚需通过真实用户访谈与可用性测试验证。

## 2. 产品定义

### 2.1 一句话定义

FCRecruiter 是一个面向足球游戏玩家和普通球迷的智能阵容分析与引援辅助 Web 应用：用户不必逐个阅读球员数据，系统会结合当前阵容、战术、伤病和足球知识，在关键决策节点提供可解释的筛选条件与球员适配分析。

### 2.2 核心问题

用户拥有大量球员数据，但缺少把数据转化为引援判断的时间、方法和专业知识。

数据并不等于结论。用户真正想知道的是：

1. 当前阵容的问题是什么；
2. 哪个位置最需要补强；
3. 应该寻找什么类型的球员；
4. 某名球员是否适合球队；
5. 这条建议依据了哪些数据，存在哪些不确定性。

### 2.3 产品形态

FCRecruiter 不是一个通用聊天机器人，也不是把若干足球 Prompt 包装成对话框。它首先是具有阵容、战术、事件和球员市场的足球产品，Agent 是嵌入业务流程的分析层。

```text
结构化足球业务数据
        ↓
确定性查询、计算和候选筛选
        ↓
Agent 汇总上下文并生成解释
        ↓
用户查看依据、调整条件并作出决定
```

## 3. 产品起源与机会判断

### 3.1 原始场景

在 Football Manager、EA Sports FC 或类似数据库中寻找球员时，用户通常需要：

- 先判断阵容短板；
- 在大量属性与位置数据中建立筛选条件；
- 逐个打开球员页面比较；
- 自己推断球员是否适配战术；
- 在伤病、阵容深度和预算之间权衡。

对于非专业玩家，这个过程耗时且认知负担高。游戏内的数据展示可以描述球员，却不一定能用新手易懂的方式回答“为什么适合我的球队”。

### 3.2 为什么不是直接使用通用 Agent

把数据封装成 MCP 或 Skill 后交给通用 Agent，理论上能够完成分析，但对普通用户存在明显门槛：

- 需要安装和配置本地 Agent；
- 需要准备数据库及连接配置；
- 工具调用路径和 Token 成本难以预估；
- 通用 Agent 的能力边界过宽，可能处理与足球无关的请求；
- 业务权限、租户隔离和结果呈现需要额外开发。

Web 应用把数据、权限、工作流和 AI 能力封装在产品内部，用户只需要在明确的业务节点触发分析。

## 4. 目标用户

### 4.1 核心用户：缺少分析时间或方法的足球游戏玩家

典型特征：

- 玩 FM、FC 生涯模式或使用足球数据库；
- 知道球队大致问题，但不会系统解释阵容结构；
- 能理解位置、能力等级和基本战术，但不想逐项研究所有属性；
- 希望快速缩小候选范围，最终仍由自己决定买谁。

核心诉求：降低信息筛选成本，而不是让 AI 代替自己玩游戏。

### 4.2 次要用户：希望辅助看球或分析新援的普通球迷

典型特征：

- 想理解新援能给球队带来什么；
- 需要把球员数据与球队战术联系起来；
- 重视结论是否有依据，但不要求专业球探级模型。

### 4.3 当前不服务的用户

- 需要真实转会定价、经纪人谈判和合同管理的职业俱乐部；
- 需要视频事件、追踪数据和专业球探报告的分析师；
- 希望使用开放式通用助手处理任意任务的用户；
- 要求系统自动完成转会决策或执行交易的用户。

这些需求超出当前数据质量、产品责任和项目规模。

## 5. 用户任务（Jobs to Be Done）

### JTBD 1：识别阵容问题

> 当我准备开始一个转会窗口时，我希望系统结合阵容强度、位置深度、战术和伤病，告诉我优先补强什么位置，以便我不用逐个检查整支球队。

### JTBD 2：形成可执行的搜索条件

> 当我知道球队存在短板但不知道如何搜索时，我希望系统把分析转化为位置、年龄、能力和预算等筛选条件，以便快速缩小候选范围。

### JTBD 3：判断具体球员是否适配

> 当我对某名球员感兴趣时，我希望系统结合球队现状和战术分析其优势、风险与适配度，以便决定是否继续考察或加入 shortlist。

### JTBD 4：理解并核验 AI 建议

> 当系统给出推荐时，我希望看到它使用了哪些球队数据和知识依据，以及结果有多大不确定性，以便判断建议是否可信。

## 6. 当前用户旅程与痛点

| 阶段 | 用户当前行为 | 主要痛点 | FCRecruiter 的机会 |
|---|---|---|---|
| 发现问题 | 浏览阵容并凭印象判断 | 容易忽略阵容深度、伤病和战术关系 | 汇总球队上下文并生成阵容诊断 |
| 定义需求 | 手动决定位置和属性门槛 | 新手不知道哪些属性真正重要 | 生成可解释的补强方向和筛选条件 |
| 搜索候选 | 反复调整筛选、逐页查看 | 数据量大，比较成本高 | 确定性筛选并保留人工调整权 |
| 考察球员 | 查看具体属性并自行匹配战术 | 难以把孤立属性映射为战术作用 | 对单个候选生成适配分析 |
| 形成决定 | 凭记忆比较多个候选 | 依据分散、容易受单一高分影响 | 展示 Evidence、风险和不确定性 |

## 7. 核心场景拆解

### 7.1 场景 A：生成球队补强建议

**触发条件**

用户进入球员市场，准备寻找新援，但尚未确定具体目标。

**所需上下文**

- 当前租户对应的球队；
- 一线队球员及位置、能力等级；
- 当前战术阵型、打法和备注；
- 当前伤病事件；
- 租户知识库中的战术或招募原则。

**系统行为**

1. 通过类型化 Tool 获取上述业务数据；
2. 使用确定性逻辑统计各位置强度和深度；
3. 由模型解释阵容问题并生成补强优先级；
4. 输出建议筛选条件、假设、不确定性和 Evidence；
5. 用户选择是否把建议应用到市场筛选。

**期望结果**

用户能够在较短时间内回答“先找什么人”，并进入候选浏览，而不是停留在泛泛的战术描述。

**成功信号**

- 用户能够理解至少一项补强建议的原因；
- 用户愿意应用或手动调整建议筛选条件；
- 推荐候选全部满足硬性数据约束；
- 分析失败时仍能继续使用普通市场筛选。

### 7.2 场景 B：分析某名球员的招募适配性

**触发条件**

用户在阵容或市场中点击一名球员，并主动选择“招募分析”。

**所需上下文**

- 候选球员的结构化数据；
- 当前球队同位置球员及阵容深度；
- 当前战术要求；
- 伤病和知识片段等辅助上下文。

**系统行为**

1. 确认候选球员存在且允许当前租户查看；
2. 对比候选与球队现有资源；
3. 分析战术适配、潜在作用、短板和风险；
4. 输出结构化结论与 Evidence，而不是只给一个分数。

**期望结果**

用户能够判断该球员值得继续考察、暂不考虑，还是需要补充更多信息。

**成功信号**

- 结论引用的球员数据与实际记录一致；
- 不把“高总评”直接等同于“适合球队”；
- 明确区分已知事实、模型推断和缺失信息。

### 7.3 场景 C：检查建议依据

**触发条件**

用户对分析结果存在疑问，或希望知道推荐来自哪里。

**系统行为**

- 展示球员数据 Evidence；
- 展示知识片段标题、来源和相关内容；
- 展示关键假设与 uncertainty；
- 当知识库没有有效命中时明确说明，而不是编造依据。

**期望结果**

用户能够判断建议的可信边界，并保留最终决策权。

### 7.4 支撑场景：维护俱乐部知识

经理上传球队战术原则、招募偏好或位置职责说明，使 Agent 的解释更贴近该租户。知识维护是增强核心分析的支撑能力，不应成为普通用户完成招募任务的前置门槛。

## 8. 用户故事与验收结果

| 优先级 | 用户故事 | 可观察的验收结果 |
|---|---|---|
| P0 | 作为经理，我希望获得当前阵容的补强优先级 | 报告至少包含阵容诊断、补强需求、建议条件和依据 |
| P0 | 作为经理，我希望把建议条件用于球员市场 | 条件可由用户确认和修改；筛选结果满足硬约束 |
| P0 | 作为用户，我希望分析一名候选球员是否适合球队 | 报告结合候选、阵容和战术，而非只复述球员属性 |
| P0 | 作为用户，我希望知道 AI 为什么这样判断 | 页面能查看 Evidence、假设和不确定性 |
| P0 | 作为用户，我希望 AI 暂时不可用时仍能浏览球员 | AI 失败不阻断市场、阵容和详情页 |
| P1 | 作为经理，我希望保存候选以便后续比较 | 可加入 shortlist，并能在同一视图比较 |
| P1 | 作为用户，我希望反馈建议是否有帮助 | 可提交轻量反馈，关联到具体分析运行 |
| P2 | 作为用户，我希望连续追问同一项分析 | 多轮上下文保持一致，并允许开始新 Thread |

## 9. 产品原则

### 9.1 Embedded，而非 Chat-first

AI 出现在“生成补强建议”和“分析该球员”等明确节点。产品不提供无边界的通用聊天入口，也不接受与足球招募无关的任务。

### 9.2 确定性逻辑优先

筛选、排序、权限、租户隔离、数值计算和候选合法性由普通代码完成。模型负责解释、归纳和在证据范围内提出建议。

### 9.3 低干预、低等待

只有当 AI 能明显减少判断成本时才调用模型。普通浏览和筛选不依赖模型；结果应尽量一次完成，不要求用户学习复杂 Prompt。

### 9.4 可解释而非伪精确

输出包含 Evidence、假设和 uncertainty。当前 uncertainty 是规则映射的离散等级，不应包装成统计置信概率。

### 9.5 人做决定

Agent 提供初筛和解释，不自动执行签约、出售、阵容调整等不可逆操作。

### 9.6 数据与权限边界优先

模型不直接访问业务数据库，也不生成 SQL。Agent 只能调用经过鉴权、租户隔离和参数校验的业务 API。

## 10. 范围边界

### 10.1 核心范围

- 多租户球队上下文；
- 球员市场与详情；
- 阵容、战术、伤病事件；
- 阵容诊断与补强方向；
- 单球员招募适配分析；
- 可追溯 Evidence 与异常降级。

### 10.2 非目标

- 通用个人助理；
- 完整模拟职业俱乐部转会部门；
- 自动谈判、报价或完成交易；
- 多 Agent 协作表演；
- 开放式 SQL 或任意代码执行；
- 用长链路自主规划替代明确、短路径的业务流程。

## 11. 需求优先级判断

### Must have：证明核心价值

- 从球队上下文生成补强建议；
- 对具体候选生成适配分析；
- 硬条件由确定性逻辑执行；
- 结果展示依据、假设和不确定性；
- AI 失败不影响基础业务功能；
- 租户和权限边界正确。

### Should have：让原型成为可评估产品

- 建议筛选条件可一键应用且可编辑；
- shortlist 与候选比较；
- 有帮助/无帮助反馈；
- 可查看一次分析的工具调用摘要与耗时，而不暴露内部思维链。

### Could have：后续增强

- 多轮追问；
- 针对不同数据源的字段映射；
- 更完整的混合检索与重排；
- 评测看板与版本对比；
- 个性化偏好学习。

### Won't have now：主动排除

- 多 Agent；
- 通用任务 Planning；
- 自动执行转会；
- 专业俱乐部级预测模型；
- 为展示技术而引入额外微服务。

## 12. 已验证事实与待验证假设

### 12.1 原型已经证明的工程可行性

- 前端、业务 Backend 和独立 Agent Service 可以连通；
- Agent 能通过工具获取阵容、战术、伤病、候选和知识数据；
- Backend 可以实施身份验证、角色权限与租户隔离；
- 模型输出可以经过 Pydantic 校验，并在失败时返回降级结果；
- PostgreSQL 与 pgvector 可以保存并按租户检索知识片段；
- 一次运行可以记录工具调用、Token、延迟、模型和 Agent 版本等轨迹。

### 12.2 尚未被证明的产品假设

- 用户是否认为建议比游戏内分析更易懂；
- 用户是否愿意等待一次完整 Agent 分析；
- 推荐是否真正减少了搜索时间；
- Evidence 的呈现是否足够清晰；
- 用户是否理解 uncertainty，而不会把它误认为数学概率；
- 知识库维护对普通用户是否过重；
- 当前结构化报告字段是否符合用户的决策顺序。

因此，当前状态应描述为“完成核心技术原型和基础招募闭环”，而不是“完成市场验证”。

## 13. 用户验证计划

### 13.1 目标样本

首轮邀请 5–8 名目标用户：

- 至少 3 名有 FM 或 FC 生涯模式经验的玩家；
- 至少 2 名不熟悉复杂球员属性的新手；
- 可补充 1–2 名关注战术分析的球迷。

### 13.2 测试任务

1. 不使用 Agent，在市场中为球队找到一名需要补强的位置候选；
2. 使用“生成招募建议”完成同一任务；
3. 查看两名候选并说明更倾向哪一名；
4. 指出系统建议使用了哪些依据；
5. 解释 uncertainty 对自己决策的影响。

### 13.3 观察指标

- 从进入市场到形成候选清单的时间；
- 用户修改建议筛选条件的次数；
- 推荐候选中的无效候选比例；
- 用户能否复述主要推荐依据；
- 任务后 1–5 分“建议是否帮助决策”；
- AI 失败时用户能否继续完成任务。

这些指标目前是验证方案，不是已经取得的项目数据。

### 13.4 访谈问题

- 你平时如何判断球队需要买什么位置？
- 最耗时或最不确定的步骤是什么？
- 哪条建议对你最有帮助，为什么？
- 哪条建议像正确的废话？
- 你是否会根据这份报告调整筛选条件？
- 哪些依据缺失会让你不信任结果？
- 你愿意维护自己的战术/知识资料吗？

## 14. 主要风险与应对

| 风险 | 表现 | 产品应对 |
|---|---|---|
| 数据与真实足球脱节 | 游戏数据不能代表现实表现 | 明确数据来源和适用边界，不包装成职业结论 |
| 模型生成空泛建议 | 结论可套用任何球队 | 强制引用球队上下文与 Evidence，增加规则评测 |
| 推荐违反硬条件 | 年龄、位置或预算不符合 | 候选由确定性查询产生，模型不能自行捏造球员 |
| 分析延迟过高 | 用户等待后放弃 | 缩短工具链、设置超时、提供进度与 fallback |
| uncertainty 被误读 | 用户认为是精确概率 | 使用文字等级并解释计算规则与边界 |
| 功能范围继续膨胀 | 技术模块多但核心体验不完整 | 以后续是否改善招募决策为唯一优先级标准 |
| 知识库维护成本高 | 用户不上传资料导致 RAG 无价值 | 提供可选默认知识，上传不是核心流程前置条件 |

## 15. 产品发现结论

FCRecruiter 最值得深化的不是“做一个迷你 OpenClaw”，而是验证一个更具体的产品命题：

> 当用户面对大量球员数据时，嵌入业务流程、受数据和权限约束的 Agent，能否比传统筛选或通用聊天工具更快地帮助用户形成可信的引援候选范围？

现有原型已经验证了主要技术链路。下一阶段的重点不是继续增加 Agent 概念，而是补齐筛选条件落地、Evidence 呈现和用户验证，使技术能力真正对应到用户决策效率。
