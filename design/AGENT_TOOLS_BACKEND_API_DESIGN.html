Typed tools & trusted execution boundary

类型化 Tool 与 Backend 安全执行层

让模型能够“查询足球数据”，但不能直接接触数据库、伪造租户身份或随意执行 SQL。本文从新手角度拆解 Agent Service 与业务 Backend 之间的完整调用链。

1. 这部分要解决什么问题？

LLM 很擅长理解“帮我找一个年轻、左脚、适合右路的球员”，但它不应该直接连接数据库。模型输出具有不确定性，也可能受到错误 Prompt 或 Prompt Injection 影响。

危险做法：
用户问题 → LLM 生成 SQL → 数据库执行 SQL → 返回结果

可能出现：
SELECT * FROM users;
DELETE FROM team_events;
SELECT * FROM players WHERE tenant_id = 其他球队;

当前设计把模型的权限缩小为：只能从预先注册的 Tool 中选择，并填写经过 Pydantic 定义的参数。真正的鉴权、租户隔离和数据库查询全部由 Backend 决定。

核心原则：模型只表达查询意图；Backend 决定这个身份能否查询、查询哪个租户、使用什么固定查询，以及最终返回哪些字段。

2. 总体架构

LLM→ToolRegistry→ Recruitment Tool→HTTP Client→ Backend 安全边界→SQLAlchemy 固定查询→ 受控响应
层主要职责不负责什么
LLM理解问题，决定调用哪个 Tool 和填写哪些业务参数。不鉴权、不选择租户、不编写 SQL。
ToolRegistryTool 白名单、参数校验、调用次数和超时边界。不直接查询业务数据库。
BusinessBackendClient发送类型化 HTTP 请求并携带可信执行身份。不实现足球查询规则。
Backend服务认证、用户/角色核验、租户隔离、固定查询、字段裁剪。不接受模型生成的 SQL。

4. 什么是“类型化 Tool”？

类型化 Tool 的输入不是任意字典，而是一个 Pydantic Model。例如确定性球员筛选使用 PlayerSearchInput：

class PlayerSearchInput(StrictToolInput):
    search: str | None
    positions: list[str]
    min_age: int | None
    max_age: int | None
    max_value_eur: int | None
    max_wage_eur: int | None
    preferred_foot: Literal["Left", "Right"] | None
    minimum_overall: Literal["D", "C", "B", "A", "A+"] | None
    limit: int  # 1 到 25

ToolRegistry 会把这个 Model 转换成 JSON Schema 发给模型。模型因而知道字段名称、类型、范围和必填规则。

{
  "positions": ["RW", "LW"],
  "max_age": 23,
  "max_value_eur": 30000000,
  "preferred_foot": "Left",
  "minimum_overall": "A",
  "limit": 5
}

extra="forbid" 会拒绝没有声明的字段：

{
  "positions": ["RW"],
  "sql": "SELECT * FROM users"
}

结果：invalid_tool_arguments，Handler 不会被调用。
类型化不等于绝对安全。Pydantic 负责格式和范围，真正的权限与租户判断仍必须在 Backend 再做一次。

5. 当前四个业务 Tool

Tool用途Backend API
get_squad读取当前租户球队阵容。GET /api/internal/agent-tools/squad
get_current_tactic读取当前阵型、打法和备注。GET /api/internal/agent-tools/tactic
get_injury_events按可选日期范围读取医疗伤病事件。POST /api/internal/agent-tools/injuries
search_players按白名单条件确定性筛选外部候选球员。POST /api/internal/agent-tools/players/search

这些 Tool 都是只读的。它们不会修改战术、创建事件、删除用户或完成转会。

确定性代码做什么？筛选、排序、范围判断、租户条件、评分转换和最大返回数量。
LLM 做什么？选择合适 Tool、组合查询条件、理解结果并生成有依据的足球分析。

6. 一次 Tool 调用发生了什么？

假设用户问：“找 5 名 23 岁以下、3000 万欧以内的左脚右边锋。”

  1. LLM 从已暴露的 Schema 中选择 search_players。
  2. LLM 只生成位置、年龄、预算、惯用脚和数量等参数。
  3. ToolRegistry.execute() 再检查该 Tool 是否位于当前 Agent 白名单。
  4. Pydantic 把模型参数验证为 PlayerSearchInput。
  5. Tool Handler 调用 BusinessBackendClient.search_players()。
  6. Client 从 AgentRunContext 取出 tenant_id 与 user_id，写入 HTTP Header。
  7. Backend 验证服务密钥，并从业务数据库重新查询用户。
  8. Backend 强制排除该租户自己的球队，并添加固定筛选条件。
  9. Backend 把具体能力值转换为 D～A+，再返回受控字段。
  10. Agent Service 再用响应 Pydantic Model 验证 Backend 响应。
  11. ToolRegistry 把 JSON 结果放入 ToolMessage，交给 LLM 继续分析。
自然语言问题
  → 结构化意图
  → 两次输入校验
  → Backend 固定查询
  → 两次输出边界
  → ToolMessage
  → LLM 解释

7. 服务认证与角色鉴权

7.1 为什么不能使用浏览器 Cookie？

浏览器访问 Backend 使用 Session Cookie 和 CSRF，但 Agent Service 是另一个服务器进程，不是浏览器。它使用服务间 Header：

X-Agent-Service-Token: <shared secret>
X-Tenant-ID: 15
X-User-ID: 29

Backend 使用恒定时间比较验证共享密钥，降低简单时序侧信道风险。密钥来自环境变量 AGENT_SERVICE_TOKEN，不能写进代码或提交到 Git。

7.2 为什么没有发送 Role Header？

Agent Service 中的 AgentRunContext.role 不能作为 Backend 的最终授权依据。HTTP Client故意不发送角色；Backend 根据 user_id + tenant_id 查询真实用户，再读取数据库里的角色。

错误思路：X-Role: manager  ← 调用方可以伪造

当前思路：
user_id + tenant_id
  → Backend 查询 User
  → 检查 User.is_active
  → 检查 Tenant.is_active
  → 读取 User.role

当前四个 Tool 都是只读查询，所以经理、球员、队医和教练四类有效角色均可使用。这个检查仍显式存在，未来可以改成按 Tool 区分，例如只有经理和队医可以读取更敏感的医疗字段。

8. 租户隔离如何实现？

Agent Service 传来的 tenant_id 只是身份声明。Backend 会要求数据库中存在同一个用户与租户的组合：

SELECT user
WHERE user.id = :user_id
  AND user.tenant_id = :tenant_id

如果攻击者把阿森纳用户 ID 和切尔西 tenant ID 拼在一起，查询不到合法组合，Backend 返回 403，且不会透露用户到底是否存在。

通过身份检查后，每个查询还会再次注入租户或球队边界：

数据强制边界
球队阵容Player.club_team_id == principal.user.tenant.club_team_id
当前战术TeamTactic.tenant_id == principal.tenant_id
伤病事件TeamEvent.tenant_id == principal.tenant_id 且类型必须是 medical
球员市场强制排除当前租户球队的球员
纵深防御：身份组合检查是一层，具体查询里的租户条件是另一层。即使未来某层代码改错，另一层仍能降低越权风险。

9. 数据边界控制

数据库模型字段很多，但 Agent 不需要看到所有内容。Backend 使用专门的响应 Schema，只返回分析所需字段。

9.1 球员字段

可以返回姓名、位置、年龄、身价、工资、惯用脚、俱乐部和国籍；不会返回头像 URL 等无关内容。具体 OVR/POT 数字会转换为：

数值范围公开等级
低于 50D
50～64C
65～74B
75～84A
85 及以上A+

9.2 数量与文本边界

  • 球员搜索最多返回 25 条。
  • 伤病事件最多返回 50 条。
  • 搜索字符串最长 100 字符。
  • 最多同时筛选 5 个位置。
  • 年龄、预算、日期范围都经过 Pydantic 校验。

这些限制同时控制数据泄露面、数据库负载和最终传给模型的 Token 数量。

10. 为什么模型无法生成 SQL？

模型看到的 Tool Schema 中根本没有 sql、table 或 order_by 字段。Agent Service 与 Backend 都使用 extra="forbid" 拒绝额外参数。

Backend 查询代码由开发者预先写好：

filters = [排除当前球队]

if payload.max_age is not None:
    filters.append(Player.age <= payload.max_age)

if payload.max_value_eur is not None:
    filters.append(Player.value_eur <= payload.max_value_eur)

select(Player).where(*filters).limit(payload.limit)

模型只能决定“max_age=23”，不能决定 SQL 结构、表名或字段名。这种方式称为参数化的确定性查询边界。

不要新增通用 execute_sql Tool。即使声称“只允许 SELECT”，SQL 解析、函数滥用、跨租户 Join、资源耗尽和间接数据泄露仍然很难完整防御。为具体业务意图定义窄 Tool 更安全，也更容易评测。

11. 失败、超时与异常降级

ToolRegistry 不把异常直接抛给模型，而是转换成统一结果：

{
  "tool_name": "search_players",
  "tool_call_id": "call-1",
  "ok": false,
  "value": null,
  "error_code": "tool_timeout",
  "error_message": "Tool execution timed out"
}
错误出现条件
tool_not_allowed模型请求了当前 Agent Definition 未授权的 Tool。
unknown_toolTool Registry 中不存在该名称。
invalid_tool_arguments参数类型、范围、组合或额外字段不合法。
tool_timeout执行超过 Runner 为单个 Tool 设置的时间。
tool_execution_errorBackend 拒绝请求、网络失败或返回非法结构。

原始内部异常不会返回模型，避免泄露数据库、内部地址或认证细节。模型可以看到受控错误，并决定换一个 Tool 或在最终报告中说明数据不足。

12. 如何装配和使用？

12.1 环境变量

# Backend 和 Agent Service 使用相同密钥
AGENT_SERVICE_TOKEN=请使用高强度随机值

# Agent Service 配置
BUSINESS_BACKEND_URL=http://127.0.0.1:8000/api
BUSINESS_BACKEND_TIMEOUT_SECONDS=5

12.2 创建 Tool Registry

from agent_service.app.recruitment import (
    RECRUITMENT_TOOL_NAMES,
    build_recruitment_tools_from_settings,
)

registry = build_recruitment_tools_from_settings()

12.3 交给 Runner

runner = AgentRunner(
    model=model_adapter,
    tools=registry,
    output_model=RecruitmentReport,
    fallback_factory=recruitment_fallback,
    allowed_tools=RECRUITMENT_TOOL_NAMES,
)

result = await runner.run(
    question="推荐一名年轻左脚右边锋",
    system_prompt=agent_definition.system_prompt,
    context=AgentRunContext(
        tenant_id=tenant_id,
        user_id=user_id,
        role=role,
    ),
)

allowed_tools 很重要：注册进进程不等于授权给当前 Agent。Runner 暴露 Schema 时检查一次，Tool 执行时还会再次检查。

13. 当前设计的限制与演进方向

当前已完成 四个只读 Tool、两层参数校验、服务密钥认证、Backend 用户与角色重建、租户隔离、确定性查询、评分脱敏、错误与超时边界。
后续可以增强 密钥轮换、mTLS、每个 Tool 的细粒度角色策略、请求 ID 与审计日志、限流、重试策略、服务健康熔断和真实 PostgreSQL 集成测试。

共享密钥适合当前学习项目和本地部署，但大型生产系统通常会使用短期服务凭证、mTLS 或工作负载身份。不要把当前方案包装成“零信任基础设施”。

当前角色策略允许四类有效用户使用全部只读分析 Tool。所谓“角色鉴权”在这里表示 Backend 会从数据库核验真实角色并应用显式允许集合；尚未实现经理、教练、球员、队医之间不同的 Tool 读取权限。

14. 新手推荐阅读顺序

  1. 先看 recruitment/tool_schemas.py，理解模型可以填写哪些字段。
  2. 再看 recruitment/tools.py，理解 ToolDefinition 如何把 Schema 和 Handler 绑定起来。
  3. 看 runtime/tools.py，重点理解白名单、Pydantic 校验、超时和错误转换。
  4. 看 recruitment/backend_client.py，观察身份 Header 和响应校验。
  5. 看 Backend 的 agent_tools/dependencies.py，理解为什么不信任上游 role。
  6. 最后看 Backend 的 agent_tools/api.py，逐个寻找强制租户条件与固定筛选。

配套测试：agent_service/tests/test_recruitment_tools.py 验证类型化调用；backend/tests/test_agent_tools.py 验证服务认证、跨租户拒绝和响应字段边界。

一句话总结LLM 提出受约束的业务意图，Backend 使用可信身份执行固定查询，模型永远不直接拥有数据库能力。
