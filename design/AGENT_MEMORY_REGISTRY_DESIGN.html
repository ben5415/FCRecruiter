Beginner-friendly design notes

Agent 短期记忆与版本注册

从“一次提问”走向“可靠的多轮对话”：理解 Thread、Message、滚动摘要、上下文裁剪，以及为什么一次旧对话必须固定在特定 Agent 版本上。

当前实现说明

Agent Definition Registry 已从运行链路移除。当前只有一个 Recruitment Agent，其 Prompt、Tool 白名单和输出 Schema 直接由代码定义，启动即可使用。本页关于 Registry 的章节只保留为早期方案记录，不代表当前代码。

1. 这部分解决什么问题？

原来的 AgentRunner.run() 只知道本轮的系统提示和用户问题。函数结束后，局部变量 messages 消失，下一次请求不知道用户刚才说过什么。

第一次请求：用户问「我们缺一个什么样的边锋？」
第二次请求：用户问「那第二个人呢？」

没有 Memory 时，模型不知道“第二个人”指谁。

新的 Memory 模块负责保存对话，并在下一次调用模型前恢复适量历史。Agent Registry 则负责回答另一个问题：这段对话究竟在使用哪一版 Prompt、哪一组 Tool、哪一种输出结构？

业务请求→发现 Agent 版本→ 读取 Memory→裁剪上下文→ AgentRunner→保存新消息
核心原则：数据库保存事实，Context Builder 决定本轮给模型看什么，Runner 只负责执行 Agent Loop。三者不要混在一个类里。

3. Thread 与 Message

3.1 Thread 是对话容器

ConversationThread 可以理解为聊天软件里的一次独立会话。一个用户可以创建多个 Thread，例如“夏窗左边锋分析”和“欧冠战术分析”。

字段含义
tenant_id / user_idThread 属于哪个球队和哪个用户，也是读取时的隔离条件。
agent_key使用哪一种 Agent，例如 recruitment。
agent_version创建时固定的版本，之后不会自动漂移。
revisionThread 修改版本，用于发现并发写入冲突。
next_sequence下一条消息应获得的连续序号。
current_summary_version当前应该使用第几版滚动摘要。
summarized_through_sequence历史消息已经总结到第几条。

3.2 Message 是不可混淆的有序记录

ConversationMessage 保存消息角色、内容和 sequence。角色不是装饰：模型会以不同权限解释 system、user、assistant 和 tool 消息。

sequence=1  role=user       “分析当前阵容”
sequence=2  role=assistant  “我需要先查询阵容”
sequence=3  role=tool       {"players": [...]}
sequence=4  role=assistant  “右边锋深度不足”

数据库对 (thread_id, sequence) 设置唯一约束，确保同一 Thread 不会出现两个“第 4 条消息”。

4. 滚动摘要为什么存在？

如果每轮都把全部历史发给模型，Prompt 会不断变长，延迟和 Token 成本也会持续增加。滚动摘要把较老消息压缩成一段短文本，只保留最近几条原始消息。

摘要 v1：用户希望寻找年轻、左脚、适合高位逼抢的边锋，预算约 3000 万欧。

最近消息 7：用户：优先考虑英超经验。
最近消息 8：助手：是否接受年龄放宽到 25 岁？

RollingSummaryService.roll_if_needed() 的流程是：

  1. 读取当前摘要、未被摘要的消息和 Thread revision。
  2. 保留指定数量的最近消息。
  3. 把旧摘要和更早消息交给 SummaryGenerator。
  4. 产生一条新的 ThreadSummary，版本号加一。
  5. 更新 Thread 的摘要版本和覆盖位置。
SummaryGenerator 是一个 Protocol，而不是写死某个模型。测试可以使用 Fake Summarizer；以后再接入 LangChain 模型，而不必修改存储和版本逻辑。

旧摘要不会被覆盖，而是保留为 v1、v2、v3。这让问题排查成为可能：如果 Agent 突然忘记一个约束，可以检查是哪一版摘要丢失了信息。

5. 上下文裁剪怎么工作？

MemoryContextBuilder 接收一个预算 max_estimated_tokens，输出 ContextWindow。当前实现使用字符数近似 Token 数，因此不额外绑定某个模型的 tokenizer。

第一优先级：滚动摘要提供较老对话的压缩背景。
第二优先级：最新消息从最新消息向前选择，保留连续后缀。

“连续后缀”很重要。假设预算不足以容纳第 7 条，却加入了第 6 条和第 8 条，模型会看到有缺口的上下文，可能错误理解因果关系。因此遇到第一条放不下的消息就停止向前选择。

ContextWindow 还会返回：

  • thread_revision：构造窗口时 Thread 的版本。
  • summary_version：本轮用了哪版摘要。
  • dropped_message_count：有多少未摘要消息因预算被丢弃。
  • estimated_tokens：本次上下文的估算消耗。

6. 两种版本控制不要混淆

版本解决的问题变化时机
thread.revision防止两个请求基于同一个旧状态同时写入。追加消息或保存新摘要。
summary.version保存摘要演进历史，知道本轮上下文用了哪版摘要。每次滚动摘要。
agent_version版本化 Prompt、Tool 列表和输出 Schema。注册新的 Agent Definition。

6.1 乐观锁示例

客户端 A 读到 revision = 5
客户端 B 也读到 revision = 5

A 使用 expected_revision=5 写入成功 → revision 变成 6
B 仍使用 expected_revision=5 写入      → 返回 HTTP 409

这叫乐观并发控制：平时不长期锁住数据库行，只在写入时检查“你依据的版本是否仍然是最新”。客户端收到 409 后应重新读取 Thread，再决定是否重试。

6.2 摘要生成期间也可能发生冲突

生成摘要可能需要调用模型，耗时比普通数据库操作长。在它生成期间，其他请求可能追加消息。因此保存摘要时也会检查快照里的 revision；不匹配就拒绝覆盖。

7. Agent Definition 是什么？

AgentDefinition 不是正在运行的 Agent 进程，而是一份可版本化的“Agent 配置说明书”。

字段作用
agent_key稳定名称，例如 recruitment。
version同一 key 下自动递增的版本号。
system_prompt该版本的系统提示。
tool_names该版本获准使用的 Tool 白名单。
output_schema该版本声明的结构化输出契约。
statusdraft、active 或 disabled。
注册 v1 / draft→启用 v1 / active→ 注册 v2 / draft→启用 v2→v1 自动 disabled

数据库的部分唯一索引保证同一个 agent_key 最多只有一个 active 版本。服务层在启用新版时先禁用旧版，再启用目标版本。

为什么 Thread 要固定版本？如果昨天的对话使用 v1，今天启用 v2 后强行切换，历史回答与新 Prompt/Tool 可能互相矛盾。当前设计让新 Thread 使用 v2，旧 Thread 继续记录自己创建时的 v1。

8. API 使用流程

这些接口不是直接开放给浏览器的公共接口，需要服务间密钥：

X-Agent-Service-Token: <shared secret>
X-Tenant-ID: 1
X-User-ID: 10

8.1 注册并启用 Agent

POST /agent-definitions
{
  "agent_key": "recruitment",
  "name": "Recruitment Agent",
  "description": "Analyse squad and recruitment needs",
  "system_prompt": "Use tools and return an evidence-based report.",
  "tool_names": ["get_squad", "get_current_tactic", "search_players"],
  "output_schema": {"type": "object"}
}

POST /agent-definitions/recruitment/versions/1/enable
GET  /agent-definitions/recruitment/current

8.2 创建 Thread

POST /threads
{
  "agent_key": "recruitment",
  "title": "Summer transfer window"
}

服务先发现当前 active 版本，然后把版本号写入 Thread。调用方不能自行伪造任意版本。

8.3 追加消息

POST /threads/{thread_id}/messages
{
  "role": "user",
  "content": "我们需要什么类型的右边锋？",
  "expected_revision": 0
}

成功后响应中的 thread_revision 会变为 1，下一次写入必须携带 1。

9. Memory 如何接入 Runner？

Runner 新增了 history_messages 参数，但仍不负责查数据库。推荐的上层编排如下：

# 伪代码：未来 ConversationService 的职责
thread = memory.get_owned_thread(thread_id, tenant_id, user_id)
definition = registry.get_version(thread.agent_key, thread.agent_version)

window = context_builder.build(
    thread_id=thread.id,
    tenant_id=tenant_id,
    user_id=user_id,
    max_estimated_tokens=2000,
)

result = await runner.run(
    question=current_question,
    system_prompt=definition.system_prompt,
    context=execution_context,
    history_messages=window.messages,
)

memory.append_message(...)  # 保存用户问题
memory.append_message(...)  # 保存结构化回答
await summary_service.roll_if_needed(...)

实际实现时，旧 Thread 应按 thread.agent_key + thread.agent_version 取得固定版本，而不是每轮都调用 discover_current()。当前版本发现主要用于创建新 Thread。

职责边界：ConversationService 负责“先做什么、后做什么”；MemoryRepository 负责数据；ContextBuilder 负责选择消息；AgentRunner 负责模型与 Tool 循环。

10. 数据库与迁移

Agent Service 使用独立的 AGENT_DATABASE_URL，不会把 Memory 和 Agent Definition 放进业务数据库。

agent_definitions
conversation_threads
conversation_messages
thread_summaries
alembic_version

迁移文件位于 agent_service/migrations/，执行：

make migrate-agent

当前迁移版本为 20260904_0001。真实服务密钥只通过环境变量 AGENT_SERVICE_TOKEN 提供，不应写入代码或提交到 Git。

12. 新手推荐阅读顺序

  1. 先看 memory/models.py，理解数据库里保存了什么。
  2. 再看 memory/repository.py，重点看追加消息和 revision 判断。
  3. 阅读 memory/context.py，观察数据库消息如何变成 LangChain Message。
  4. 阅读 memory/service.py，理解滚动摘要为什么要先拍快照再保存。
  5. 阅读 registry/models.py 和 registry/repository.py，理解版本状态机。
  6. 最后看两个 api.py 和 runtime/runner.py，把调用边界串起来。

建议配合测试阅读：agent_service/tests/test_memory_registry.py 展示核心规则，test_memory_registry_api.py 展示完整 HTTP 调用顺序。
