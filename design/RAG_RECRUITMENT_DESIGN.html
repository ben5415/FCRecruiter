PostgreSQL + pgvector + typed tools

足球知识 RAG 与循证引援推荐

把“数据库里的球员事实”和“足球领域知识”分开检索，再让 LLM 负责解释和综合；每个诊断、补强需求与候选推荐都保留可追踪的 Evidence。

1. 目标与边界

这个模块要回答两类不同问题：

业务事实本队有哪些球员？当前战术是什么？谁受伤？哪些候选符合年龄和预算？
领域知识高位逼抢需要什么能力？内切边锋承担什么职责？阵型宽度不足通常如何补强？

业务事实来自 Backend 的结构化数据和确定性查询；领域知识来自 Agent 数据库里的知识片段。LLM 不能把知识库内容当作球员真实属性，也不能把自己的常识伪装成已检索证据。

核心原则：确定性代码找事实和候选，向量检索找相关知识，LLM 只负责把两者组织成可读、带依据的建议。

2. 新手先理解：RAG 是什么？

RAG 是 Retrieval-Augmented Generation，即“检索增强生成”。它不是训练模型，而是在调用模型前先查找相关资料，再把资料作为 Tool 结果交给模型。

用户问题→生成查询向量→检索相似片段→LLM 阅读片段→生成带引用报告

2.1 Embedding 是什么？

Embedding 模型把文本转换成一串浮点数。语义相近的文本，其向量方向通常更接近。

“高位逼抢对前锋的要求” → [0.12, -0.04, 0.81, ...]
“压迫型前锋需要哪些能力” → [0.10, -0.02, 0.78, ...]

当前数据库固定使用 1024 维向量，默认通过本机 Ollama 使用 bge-m3。文档入库和问题检索必须使用相同模型与维度，否则距离没有意义。

2.2 为什么先切片？

整本战术书作为一个向量过于粗糙，也会一次返回太多文本。系统先把文档切成约 1200 字符的片段，相邻长片段重叠约 150 字符，降低关键句刚好被切断的概率。

3. 总体架构

知识入库链路
Markdown / Text
  → split_text
  → EmbeddingAdapter.embed_documents
  → Ollama /api/embed → bge-m3 (本机推理)
  → knowledge_documents + knowledge_chunks(vector)

在线分析链路
用户问题
  → AgentRunner
  ├─ get_squad / get_tactic / get_injury_events → Backend
  ├─ search_players                           → Backend 固定筛选
  └─ search_football_knowledge                → Agent DB / pgvector
  → LLM 综合解释
  → RecruitmentReport
  → Evidence.source_id

业务 Backend 仍然是球员、阵容、战术和事件的可信数据边界。知识库只存外部足球资料及其向量，不复制实时业务事实。

5. 文档与片段如何存储？

5.1 KnowledgeDocument

字段含义
tenant_scope0 表示所有租户可见；正整数表示某租户私有。
title资料标题。
source_uri原文件或网页来源，用于回溯。
checksum规范化正文的 SHA-256，用于避免重复导入。
document_metadata作者、发布日期、资料类型等扩展信息。

5.2 KnowledgeChunk

字段含义
document_id所属文档。
chunk_index片段在文档里的顺序。
content交给模型阅读的原始片段。
token_estimate粗略 Token 数，用于未来上下文预算。
embedding1024 维 pgvector 向量。

片段 ID 使用 UUID，并直接参与 Evidence：knowledge:<chunk UUID>。

6. 一份知识文件如何入库？

  1. 读取 UTF-8 Markdown 或 Text 文件。
  2. 清理首尾空白并计算 SHA-256。
  3. 按来源、校验和与租户检查是否已导入。
  4. 按段落优先切片，超长段落使用重叠字符窗口。
  5. 批量调用本机 Ollama Embedding API。
  6. 检查返回数量和每个向量的维度。
  7. 再次检查重复，避免 Embedding 期间发生并发重复导入。
  8. 在一个数据库事务中写入文档与全部片段。
# 导入所有租户共享的知识
make knowledge ARGS='knowledge/inverted_winger.md'

# 导入租户 15 的私有资料
make knowledge ARGS='club_notes.md --tenant-id 15 --title "Club Scouting Model"'
重复导入相同来源和相同内容不会再次生成数据库记录；脚本会报告 already exists。

7. pgvector 检索如何工作？

问题先经过同一个 EmbeddingAdapter 得到查询向量。Repository 使用固定的余弦距离表达式：

distance = KnowledgeChunk.embedding.cosine_distance(query_embedding)
similarity = 1.0 - distance

WHERE document.tenant_scope = 0
   OR document.tenant_scope = current_tenant
ORDER BY distance
LIMIT :limit

系统还会过滤低于 min_similarity 的结果。每个 SearchHit 返回标题、来源 URI、原文片段、相似度、片段顺序和 Evidence ID。

7.1 HNSW 索引

迁移为 embedding 建立 HNSW 余弦索引。它是一种近似最近邻索引，适合从大量向量中快速找到相似项。当前小数据集即使顺序扫描也能工作，但提前建立索引让结构可以扩展。

相似不等于正确。向量检索只表示文本语义相关，不证明资料可靠，也不保证片段真的回答了问题。最终报告仍应标记不确定性，并保留来源。

8. 确定性候选筛选与知识 Tool 如何配合？

Tool回答的问题不能回答什么
search_players哪些真实球员满足位置、年龄、预算、惯用脚和等级条件？为什么这种球员适合某种战术。
search_football_knowledge相关战术角色和招募原则是什么？某个球员实际拥有哪些未提供的属性。
错误：知识说“内切边锋通常需要左脚”
      → 推断候选 A 一定是左脚

正确：search_players 明确返回候选 A preferred_foot=Left
      + 知识片段解释左脚右边锋的战术作用
      → 形成有两类证据的适配理由

因此流程应该先诊断阵容和补强需求，再使用确定性条件缩小候选集，最后用知识解释角色适配与风险。

9. Evidence 如何保留来源？

各 Tool 返回稳定的 evidence_source_id：

来源ID 格式
当前阵容squad:current
当前战术tactic:current
球队事件event:<event_id>
候选球员player:<player_id>
知识片段knowledge:<chunk UUID>

Prompt 要求模型原样复制 ID；Pydantic 会检查 source_type 与 ID 前缀是否匹配。候选推荐还必须包含对应的 player:<player_id>，否则整份报告校验失败并进入降级结果。

{
  "source_type": "knowledge",
  "source_id": "knowledge:7b8c...",
  "description": "Inverted winger role principles"
}
Evidence 保存的是“这条结论依据了哪个数据对象或知识片段”，不是模型的隐藏思维过程。前端以后可以根据 source_id 提供跳转或展开原文。

10. 阵容诊断到推荐报告的完整流程

  1. get_squad 获取当前阵容结构。
  2. get_current_tactic 获取阵型、打法和备注。
  3. get_injury_events 获取影响可用性的医疗事实。
  4. LLM 基于这些事实提出一个或多个 RecruitmentNeed。
  5. search_players 用确定性条件筛选候选。
  6. search_football_knowledge 检索角色、战术和评估原则。
  7. LLM 生成原因、风险、假设和不确定性。
  8. Pydantic 验证 RecruitmentReport 与 Evidence。
RecruitmentReport
├── summary
├── needs[]
│   ├── position / priority / reason
│   └── evidence[]
├── candidates[]
│   ├── player_id / fit_grade
│   ├── reasons[] / risks[]
│   └── evidence[]  ← 必须有 matching player:id
├── assumptions[]
└── uncertainty

factory.py 使用 DeepSeek、LangChainModelAdapter、五个 Recruitment Tool 和 AgentRunner 完成真实装配。默认最多 6 次模型步骤和 8 次 Tool 调用。

业务 Backend 最终调用受服务密钥保护的入口：

POST /recruitment/analyse
X-Agent-Service-Token: ...
X-Tenant-ID: 15
X-User-ID: 29

{
  "question": "诊断当前阵容并推荐一名右边锋"
}

该入口直接使用代码中的 Recruitment Prompt、Tool 白名单和结构化输出 Schema。浏览器不会获得服务密钥，而是通过业务 Backend 的登录态代理接口调用。

11. 知识检索的租户隔离

知识分为全局与租户私有两类：

tenant_scope = 0   → 所有球队都能检索
tenant_scope = 15  → 只有 tenant 15 能检索

模型不能在 Tool 参数中指定 tenant_id。Tool Handler 从可信 AgentRunContext 读取当前租户，然后 Repository 强制添加可见性条件。

Agent 数据库没有业务 Tenant 外键，因为它和 Backend 是独立数据库。因此 tenant_id 的真实性来自已经认证的服务调用链；检索查询本身仍必须强制加 tenant_scope 条件。

12. 配置、迁移与运行

12.1 准备 Ollama 模型

# 下载一次，之后可离线推理
ollama pull bge-m3

# Linux CLI 安装通常需要显式启动；Ollama Desktop 一般会自动运行服务
ollama serve

# 验证服务和模型（另开终端）
curl http://127.0.0.1:11434/api/embed \
  -d '{"model":"bge-m3","input":"高位逼抢需要什么类型的前锋？"}'

bge-m3 输出 1024 维向量，支持中英文等多语言检索。首次推理需要将模型载入内存，后续请求通常更快。

WSL 注意：如果 Ollama 安装在 Windows、Agent Service 运行在 WSL，必须先确认 WSL 能访问 Ollama。无法使用 127.0.0.1:11434 时，应把 OLLAMA_BASE_URL 改为 Windows 主机可访问地址，并配置 Ollama 监听范围。

12.2 系统级 pgvector 扩展

Python 包 pgvector 只提供客户端类型；PostgreSQL 服务器还必须安装扩展。当前 Ubuntu + PostgreSQL 18 可执行：

sudo apt-get install -y postgresql-18-pgvector
make migrate-agent

迁移先创建知识表，再把向量列统一为 vector(1024) 并建立 HNSW 余弦索引。更换模型前已有向量必须清空并重新生成，不能把旧模型向量直接转换为新模型向量。

12.3 环境变量

AGENT_DATABASE_URL=postgresql+psycopg://.../fc26_agent

EMBEDDING_BACKEND=ollama
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_EMBEDDING_MODEL=bge-m3
EMBEDDING_DIMENSIONS=1024
EMBEDDING_TIMEOUT_SECONDS=20
KNOWLEDGE_CHUNK_SIZE=1200
KNOWLEDGE_CHUNK_OVERLAP=150

DEEPSEEK_API_KEY=...
DEEPSEEK_MODEL=deepseek-chat

Agent Service 通过 Ollama 的 /api/embed 接口调用本机模型，不需要在 Python 虚拟环境安装 PyTorch，也不产生按次 API 费用。如果设备首次加载模型超过 20 秒，可以单独调大 EMBEDDING_TIMEOUT_SECONDS。

12.4 请求如何经过 Adapter

KnowledgeService
  → EmbeddingAdapter（统一接口）
  → OllamaEmbeddingAdapter
  → POST {OLLAMA_BASE_URL}/api/embed
     {"model": "bge-m3", "input": ["片段一", "片段二"]}
  ← {"embeddings": [[...1024维...], [...1024维...]]}
  → 校验数量与维度
  → 写入 pgvector

Adapter 只转换协议并验证响应，不负责 SQL、切片或租户判断。因此测试可以注入假的 HTTP Client，未来也能在不改 KnowledgeService 的情况下替换 Provider。

12.5 Agent 配置

当前只有一个 Recruitment Agent。经理可在前端 Agent Settings 注册当前代码中的 Prompt、Tool 白名单和输出 Schema 快照，并启用或禁用版本；分析请求在运行时发现当前启用版本。页面不允许编辑 Prompt 或上传 Tool，因此这里只实现版本治理，不是通用 Agent 平台。

13. 测试与后续评测

当前单元测试不调用真实模型或真实 Ollama 服务：

  • 验证段落切片和长文本重叠。
  • 验证 Ollama 请求地址、模型名、批量输入及响应维度。
  • 验证兼容 HTTP Provider 的响应排序和维度。
  • 验证知识 Tool 使用可信 tenant_id。
  • Fake LLM 依次调用阵容、候选筛选和知识检索。
  • 验证 Tool 返回的 Evidence ID 被写入结构化报告。
  • 验证缺少匹配球员 Evidence 的候选会被拒绝。

下一阶段评测不应只判断语言是否流畅，还应检查：

指标示例
Retrieval relevance返回片段是否真正讨论用户要求的战术角色。
Groundedness报告中的事实能否在 Tool 结果中找到。
Citation validityEvidence ID 是否真实存在且类型匹配。
Candidate constraint pass rate推荐球员是否全部满足确定性筛选条件。
Tool selection问题是否触发了需要的业务或知识 Tool。

14. 当前限制与诚实边界

  • Embedding 维度固定为 1024，更换不同维度模型需要新迁移和重新向量化。
  • 当前切片器按段落和字符处理，尚未理解 Markdown 标题层级。
  • 知识来源尚无可信度评级、有效期和人工审核状态。
  • 相似度阈值默认 0.25，需要用真实资料和问题校准。
  • Evidence 验证能检查 ID 格式和候选 ID，但不能自动证明自然语言结论完全忠于原文。
  • Embedding 不产生按次 API 费用，但本机推理仍消耗 CPU、内存和时间；LLM 调用成本仍需通过观测数据统计。
  • 当前没有 Ollama 自动重试或熔断；服务未启动、模型不存在和请求超时都会作为明确异常返回。
  • 尚未提供知识管理 Web 页面；当前通过脚本导入。

这些限制不会破坏核心边界：模型仍不能生成 SQL，候选仍由确定性代码筛选，知识片段仍可定位到数据库记录和原始来源。

15. 新手推荐阅读顺序

  1. 阅读 knowledge/schemas.py，先知道输入和输出长什么样。
  2. 阅读 knowledge/service.py，理解切片、去重、Embedding 和检索编排。
  3. 阅读 knowledge/embeddings.py，理解为什么需要 Provider Adapter。
  4. 阅读 knowledge/models.py 与迁移，理解 vector 列和 HNSW 索引。
  5. 阅读 knowledge/repository.py，找到余弦距离和 tenant_scope 条件。
  6. 阅读 recruitment/tools.py，看知识检索如何成为 Agent Tool。
  7. 阅读 recruitment/prompt.py 和 schemas.py，理解 Prompt 规则与代码校验的区别。
  8. 最后阅读 test_knowledge_recruitment.py，跟踪完整 Fake Agent Loop。

一句话复述：结构化 Backend Tool 提供球队与球员事实，pgvector Tool 提供相关足球知识，LLM 负责解释，Evidence 把报告重新连接到原始数据和知识片段。
