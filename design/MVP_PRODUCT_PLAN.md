## 1. MVP 目标

### 1.1 目标用户

希望减少阵容分析和球员筛选成本，但仍想保留最终选择权的足球游戏玩家。

### 1.2 核心价值假设

如果系统能够把阵容、战术、伤病和球员数据组合为可解释的补强建议，并把建议转化为可执行的市场筛选条件，那么用户可以更快地形成合理候选范围，而不必逐个检查大量球员。

### 1.3 MVP 要证明的事情

MVP 不需要证明 FCRecruiter 能代替球探或完成全部俱乐部管理。它只需要证明：

1. 用户能从球队上下文得到明确的补强方向；
2. 用户能把补强方向落实为候选球员；
3. 用户能分析某个候选与球队的适配性；
4. 用户能理解建议的依据和边界；
5. AI 不可用时，基础球员市场仍然可用。

## 2. MVP 闭环

```mermaid
flowchart LR
    A[登录球队账号] --> B[查看阵容、战术与事件]
    B --> C[进入球员市场]
    C --> D[生成招募建议]
    D --> E[查看诊断、补强需求与 Evidence]
    E --> F[确认或修改建议筛选条件]
    F --> G[浏览确定性候选列表]
    G --> H[打开球员详情]
    H --> I[生成单球员适配分析]
    I --> J[继续考察或放弃]
```

闭环的终点不是“AI 给出答案”，而是用户形成一个有依据的候选决策。

## 3. 版本范围

### 3.1 P0：MVP 必须具备

| 模块 | 能力 | 当前状态 | MVP 补齐项 |
|---|---|---|---|
| 账号与租户 | 登录、角色权限、租户隔离 | 已实现 | 做一次跨租户回归验证 |
| 阵容 | 查看租户球队全部球员 | 已实现 | 保持只读稳定性 |
| 战术 | 保存当前阵型、打法和备注 | 已实现 | 明确无战术时的分析提示 |
| 球队事件 | 记录伤病等球队上下文 | 已实现 | 保证 Agent 只读取当前租户事件 |
| 球员市场 | 搜索、分页、查看详情 | 已实现 | 保持 AI 失败时仍可独立使用 |
| 招募建议 | 生成阵容诊断、补强需求和建议条件 | 基本实现 | 完整呈现 Evidence 与建议条件 |
| 条件落地 | 把建议转化为市场筛选 | 部分实现 | 支持全部已输出条件，不只应用位置 |
| 球员适配 | 对指定候选生成招募分析 | 基本实现 | 明确优势、风险、战术适配与证据 |
| 异常降级 | 模型或工具异常时返回可理解结果 | 已实现 | 前端给出可恢复操作，不只显示错误 |
| 知识检索 | 按租户检索足球知识 | 已实现 | 无命中时明确标记，不强制用户上传 |

### 3.2 P1：MVP 后首轮迭代

- shortlist：保存感兴趣的候选球员；
- 候选比较：并排比较 2–3 名球员及各自适配结论；
- 轻量反馈：有帮助/无帮助，加可选原因；
- 运行摘要：展示本次使用的数据类型、工具状态和耗时；
- 建议条件编辑：应用前允许用户调整，而非直接覆盖当前搜索；
- 基础埋点：记录核心漏斗和失败原因。

### 3.3 P2：验证价值后再考虑

- 多轮对话与 Thread 历史；
- 自动滚动摘要真正接入招募流程；
- 检索重排和混合检索；
- Agent 版本效果对比和评测看板；
- 多数据源导入与统一字段映射；
- 根据用户反馈学习偏好。

### 3.4 明确不进入 MVP

- Multi-Agent；
- 通用 ReAct/Planning 工作台；
- Reflection 自我改写循环；
- 自动报价、签约或出售球员；
- 真实转会成功率预测；
- 开放式聊天与非足球任务；
- 为展示架构而继续拆分微服务。

## 4. 页面与功能要求

### 4.1 球员市场页

用户可以：

- 使用普通搜索与分页浏览球员；
- 点击“生成招募建议”；
- 查看阵容问题与补强优先级；
- 查看系统建议的筛选条件；
- 在应用筛选前修改条件；
- 查看每条建议的依据、假设和不确定性；
- 在 AI 失败时关闭分析面板并继续手动浏览。

### 4.2 球员详情页

用户可以：

- 查看已经按产品规则转换后的球员能力等级；
- 点击“招募分析”；
- 查看球员相对当前阵容和战术的作用；
- 区分优势、风险、缺失信息和最终建议；
- 展开 Evidence 查看数据或知识来源；
- 返回市场时保留原页码和筛选状态。

### 4.3 知识库页

经理可以上传、查看和删除本租户知识。知识库是增强分析的可选配置，不应阻止未上传资料的租户使用基础招募分析。

### 4.4 Agent 设置页

保留最小的 Agent Definition 管理能力，用于注册版本、启用/禁用和发现当前版本。MVP 不将其扩展为通用 Agent 市场或编排平台。

## 5. Agent 产品契约

### 5.1 输入边界

Agent 只接收完成当前招募任务所需的信息：

- 当前用户和租户身份；
- 阵容、战术和伤病摘要；
- 候选筛选条件或指定球员 ID；
- 与任务相关的租户知识片段。

模型不能直接连接业务数据库，不能生成并执行 SQL，也不能绕过 Backend 获取其他租户数据。

### 5.2 确定性逻辑职责

- 用户、角色与租户鉴权；
- 球员存在性检查；
- 市场查询、分页、排序与硬条件筛选；
- 能力等级换算；
- 工具参数校验；
- 候选合法性验证；
- 超时、调用次数和执行步骤限制。

### 5.3 模型职责

- 综合多类上下文；
- 解释阵容结构问题；
- 归纳补强需求；
- 解释候选与战术的适配关系；
- 用普通用户可理解的语言说明风险和取舍。

### 5.4 结构化输出

招募报告至少包含：

- 报告标题与摘要；
- 阵容诊断；
- 补强需求及优先级；
- 建议筛选条件；
- 候选推荐或指定球员分析；
- Evidence；
- assumptions；
- uncertainty；
- 执行摘要或降级原因。

所有模型输出视为不可信输入，必须通过 Pydantic Schema 校验。首次输出不合法时允许一次受控修复；仍失败则返回结构化 fallback。

## 6. 正常流程与异常流程

### 6.1 正常流程

1. 前端向业务 Backend 发起分析请求；
2. Backend 验证会话并确认用户租户；
3. Backend 使用服务身份请求 Agent Service；
4. AgentRunner 根据当前 Agent Definition 加载模型、工具和限制；
5. 模型选择受控工具获取业务数据和知识；
6. Backend 内部接口再次验证服务身份、用户状态和租户边界；
7. Agent 生成结构化报告并通过 Pydantic 校验；
8. 运行轨迹写入 Agent 数据库；
9. Backend 把报告返回前端；
10. 前端展示建议，并由用户决定是否应用筛选条件。

### 6.2 异常流程

| 异常 | 系统行为 | 用户可继续做什么 |
|---|---|---|
| 模型超时 | 终止当前步骤并返回降级报告 | 重试或继续手动筛选 |
| 工具超时 | 记录失败工具，不无限重试 | 查看有限分析或手动浏览 |
| 结构化输出错误 | 进行一次格式修复，失败后 fallback | 重新生成或关闭面板 |
| Ollama 不可用 | 知识上传/检索返回明确服务错误 | 修复本地服务，基础市场不受影响 |
| 知识无命中 | 报告标记缺少知识证据 | 使用结构化球队数据完成基础分析 |
| 无当前战术 | 明确提示该假设缺失 | 先填写战术或接受较高不确定性 |
| 用户越权 | Backend 拒绝请求，不调用模型 | 返回无权限提示 |

## 7. MVP 验收标准

### 7.1 功能验收

- 用户可以从市场页完成一次球队补强分析；
- 报告使用当前租户的阵容、战术和伤病数据；
- 用户可以把报告中的位置、年龄、预算、工资、惯用脚和最低能力等已支持条件用于候选查询；
- 用户可以进入候选详情并完成一次适配分析；
- 返回市场后保留分页和筛选状态；
- AI 不可用时，市场浏览、搜索和详情仍然正常。

### 7.2 AI 质量验收

- 输出符合 RecruitmentReport Schema；
- 推荐球员全部来自工具返回结果，不出现虚构候选；
- 推荐球员满足确定性硬条件；
- 报告至少引用一项有效球队数据 Evidence；
- 知识引用能够定位到文档或片段来源；
- 缺少信息时以 assumption 或 uncertainty 表达，不把推断写成事实；
- 预设离线样例的规则评测通过率达到发布门槛。

门槛的具体数值需要先建立固定评测集后确定，不在没有数据时虚构百分比。

### 7.3 安全与隔离验收

- 普通用户不能通过请求参数切换 tenant_id；
- Agent 的业务数据必须来自 Backend 内部 API；
- 其他租户的球队事件和知识片段不可被检索；
- Tool 参数经过 Pydantic 校验；
- 模型不能提交 SQL、任意 URL 或任意代码作为工具参数执行。

### 7.4 可用性验收

- 新用户无需编写 Prompt 即可触发两类核心分析；
- 分析面板能区分事实依据、模型解释和不确定性；
- 用户知道如何应用、修改或拒绝建议；
- 错误信息说明下一步操作，而不是只显示内部错误码。

## 8. 成功指标

### 8.1 北极星指标候选

**有效候选形成率**：触发招募建议后，在一次会话内应用/修改筛选并查看至少一名候选详情的分析次数，占招募建议总次数的比例。

该指标同时覆盖“建议可理解”“条件可执行”和“用户继续决策”，比单纯统计模型调用次数更接近产品价值。

### 8.2 漏斗指标

```text
进入市场
  → 请求招募建议
  → 成功获得报告
  → 应用或修改建议条件
  → 查看候选详情
  → 请求候选适配分析
  → 保存候选或给出有帮助反馈
```

建议观测：

- 招募建议触发率；
- 报告成功率和 fallback 率；
- 建议条件应用率、修改率；
- 候选详情查看率；
- 单球员分析触发率；
- 有帮助反馈比例；
- 从进入市场到形成候选的中位耗时。

### 8.3 技术运行指标

- 端到端延迟；
- 模型调用次数和工具调用次数；
- Token 消耗；
- 各工具成功率和 P95 延迟；
- Schema 修复率；
- 无效候选率；
- Evidence 完整率；
- 按模型和 Agent 版本聚合的规则评测结果。

以上为待接入或待形成基线的指标，不应在简历或汇报中写成已取得的业务成果。

## 9. 埋点方案

| 事件名 | 触发时机 | 关键字段 |
|---|---|---|
| `recruitment_brief_requested` | 点击生成招募建议 | tenant、user role、agent version |
| `recruitment_brief_completed` | 报告成功返回 | run_id、latency、fallback、uncertainty |
| `recruitment_brief_failed` | 请求失败 | error category、stage、retryable |
| `suggested_filter_applied` | 应用建议条件 | applied fields、modified fields |
| `player_detail_opened` | 打开候选详情 | player_id、source page |
| `player_fit_requested` | 点击单球员分析 | player_id、agent version |
| `player_fit_completed` | 适配报告返回 | run_id、latency、fallback |
| `evidence_expanded` | 用户展开依据 | evidence type、report type |
| `analysis_feedback_submitted` | 提交反馈 | run_id、helpful、reason code |

原则：不记录密码、Token、完整 Prompt 或与产品分析无关的个人信息；运行轨迹与产品行为事件使用 `run_id` 关联。

## 10. 离线评测计划

### 10.1 固定测试集

建立少量但可重复的案例，每个案例包含：

- 租户与球队快照；
- 当前战术；
- 伤病数据；
- 用户任务；
- 允许出现的候选集合；
- 必须调用和禁止调用的工具；
- 最低 Evidence 要求；
- 人工编写的质量检查点。

首版覆盖以下情形：

1. 某位置深度明显不足；
2. 主力受伤造成短期补强需求；
3. 总评高但战术不适配的候选；
4. 战术信息缺失；
5. 知识库无命中；
6. 工具超时或模型输出不合法；
7. 候选不满足年龄或预算硬约束；
8. 跨租户数据不可见。

### 10.2 规则评测

- Pydantic Schema 是否通过；
- 工具选择是否符合任务；
- 候选是否来自工具结果；
- 候选是否满足硬条件；
- Evidence 是否完整；
- 假设和不确定性是否存在；
- fallback 是否与实际失败原因一致。

### 10.3 LLM-as-judge 边界

LLM-as-judge 只用于少量难以完全规则化的维度，例如：

- 阵容诊断是否具体；
- 战术适配解释是否自洽；
- 报告是否清晰且避免重复；
- 风险与取舍是否充分。

它不替代候选合法性、权限和 Schema 等确定性检查，也不应成为唯一发布门槛。

## 11. 迭代优先级

### 第 1 阶段：补齐已有闭环

1. 前端完整展示 Evidence；
2. 把所有已生成的建议条件接入市场筛选；
3. 统一正常、无数据和 fallback 的页面状态；
4. 建立 8–12 个固定离线评测案例；
5. 对核心闭环做一次端到端回归。

### 第 2 阶段：验证真实价值

1. 增加轻量用户反馈；
2. 接入核心漏斗埋点；
3. 邀请 5–8 名目标用户完成任务测试；
4. 比较手动筛选与 Agent 辅助的完成时间和错误；
5. 根据观察结果调整报告顺序和字段。

### 第 3 阶段：增强决策体验

1. 实现 shortlist；
2. 实现候选比较；
3. 提供运行摘要和失败诊断；
4. 在有数据支持后优化检索、Prompt 或模型。

只有核心漏斗和用户反馈证明价值后，才进入 Memory、多轮对话、复杂 Agent 编排等扩展。

## 12. 当前完成度判断

### 已经完成

- 多租户业务原型与四类角色权限；
- 阵容、市场、球员详情、战术、事件和知识维护页面；
- 独立 Agent Service；
- AgentRunner、ModelAdapter、ToolRegistry 与类型化工具；
- Backend 服务间鉴权和租户边界；
- 两类招募分析入口；
- pgvector 知识检索与结构化 Evidence；
- 执行限制、结构化校验、异常降级和轨迹记录；
- 基础规则评测及少量 LLM-as-judge 能力。

### 部分完成

- 建议条件已生成，但前端尚未完整应用所有字段；
- Evidence 已进入响应结构，但用户侧呈现仍需加强；
- Memory 和滚动摘要具备数据结构与基础代码，但没有真正形成核心产品体验；
- Agent Definition 可管理版本，但部分运行配置仍与代码耦合；
- 执行轨迹已记录，但缺少面向产品分析的查询和看板。

### 尚未完成

- shortlist 与候选比较；
- 用户反馈闭环；
- 固定版本化评测集与发布门槛；
- 产品行为埋点和真实用户验证；
- 可复现部署说明与上线环境；
- 面向实际使用的完整端到端验收。

## 13. MVP Definition of Done

当以下条件全部满足时，才把项目称为“完成可验证 MVP”，而不只是技术原型：

- [ ] 一名新用户无需指导即可完成完整招募闭环；
- [ ] 建议的所有硬筛选条件能够落到真实市场查询；
- [ ] 用户可以检查球员数据和知识来源 Evidence；
- [ ] AI 失败时用户仍能完成手动筛选；
- [ ] 租户隔离、角色权限和候选合法性回归测试通过；
- [ ] 固定离线评测集可以重复运行并比较 Agent 版本；
- [ ] 核心产品漏斗有埋点；
- [ ] 至少完成一轮 5–8 名目标用户的任务测试；
- [ ] 根据真实反馈完成一次产品迭代；
- [ ] README 能指导他人在新环境中启动并体验核心流程。

## 14. 项目叙事建议

在产品经理或技术产品经理语境中，项目不应只描述“做了多少 Agent 模块”，而应按以下逻辑表达：

1. 从足球游戏玩家筛选成本高的问题出发，定义嵌入式招募辅助场景；
2. 将模糊的“帮我买人”拆成阵容诊断、条件生成、确定性筛选和候选解释；
3. 划分确定性系统与 LLM 的职责，设计权限、租户和 Evidence 边界；
4. 交付可运行原型，打通从球队上下文到球员适配分析的核心闭环；
5. 建立轨迹和评测基础，并明确下一步通过埋点和用户测试验证产品价值。

这种叙事既保留技术深度，也能体现需求拆解、范围管理、风险控制和迭代意识。
